# PR 3 — Physical cache-space accounting (Amendment #4 design note)

> **Status: DESIGN + STOP REQUEST — NOT APPROVED, NOT IMPLEMENTED.**
> Linked from `docs/decisions/PR03_STORAGE_CONTRACT_DECISIONS.md`. This note
> proposes a hard physical-byte bound for cache-owned files and records the
> contract gap that blocks implementation. It does **not** change approved
> S01–S16 semantics and is **not** a merge approval.

## Scope and definitions

- **Cache-owned file:** a regular file inside the dedicated cache namespace
  whose name was generated by `trawler-core` (`cache-v1-…` published entries and
  `tmp-v1-…` / `FsDirectory` temporary files). Local-only durable index files
  and files created by external actors are **not** cache-owned.
- **Physical byte:** the content length of a cache-owned regular file. The bound
  deliberately does **not** cover filesystem allocation overhead, metadata
  blocks, sparse-file allocation, directory entries, or bytes written by
  external actors.
- **`physical_bytes`** is the sum of cache-owned file content lengths. It is
  **not** the same as the logical `CacheStats::published_bytes`.

## Budget equation

```text
physical_bytes =
      published_length_bytes          (verified, published entries)
    + reserved_write_bytes            (admitted operations not yet on disk)
    + temp_bytes                      (in-progress temp/partial files)
    + evicting_bytes                  (published entries whose delete is running)
    + delete_failed_bytes             (deletes that failed; file still present)
    + orphaned_bytes                  (cache-owned files with no live entry)

physical_bytes <= max_cache_bytes
```

Every cache-owned content byte is charged to exactly one term at a time; when a
file transitions between terms its charge is **moved**, never duplicated or
dropped. Logical published statistics remain separate and may legitimately
differ from `physical_bytes`.

## State model and transitions

| State | On-disk reality | Charge | Transitions |
|---|---|---|---|
| `Absent` | no file | 0 | `reserve` → `Reserved` |
| `Reserved` (write admitted, not dispatched) | no file yet | `delta` (see overlap) | cancel → `Absent`; dispatch → `Temp` |
| `Temp` | temp file (and maybe old destination) | max(on-disk old + temp) | success → `Published`; failure/cancel → `Orphaned` or `Absent` |
| `Published` verified | one destination file | file length | pin/unpin; evict → `Evicting` |
| `Evicting` | destination file still present | file length | delete ok → `Absent`; delete err → `DeleteFailed` |
| `DeleteFailed` | file still present | file length | explicit cleanup ok → `Absent` |
| `Orphaned` | cache-owned file, no live entry | file length | verify+reuse → `Published`; remove → `Absent` |

`Reserved` may overlap `Temp` transiently; the overlap term must reserve the
**maximum** simultaneous physical occupancy, not just `content.length`.

## The temp/destination overlap caveat

`FsDirectory::atomic_write` creates a same-parent temporary file and renames it
over the destination. When the destination already exists (for example a
re-materialization of the same content-addressed key), the old destination and
the new temp coexist, so the operation can temporarily hold **two** copies.

- First write to a key: physical delta ≈ `content.length` (temp), then rename.
- Re-write of an existing key: physical delta ≈ `2 × content.length`
  (old destination + temp) until rename.

A logical reservation of `content.length` alone therefore does **not** prove a
hard physical bound. A compliant design must either (a) reserve the maximum
overlap (`destination_length + content.length`), or (b) avoid simultaneous
destination/temp coexistence for content-addressed keys (for example by
removing/renaming the destination first, which weakens atomic visibility and is
rejected). Option (a) is proposed.

## Admission behaviour

`reserve(bytes)` computes the maximum physical delta for the pending operation
and admits only when `physical_bytes + delta <= max_cache_bytes`. If it cannot
fit, it requests eviction of charged, unpinned, non-evicting entries and retries.
If no progress is possible it returns the existing typed
`StorageError::LimitExceeded`. Admission is asynchronous and never blocks or
spins on an executor thread.

## Failed delete is not freed capacity

A `delete` that returns an error is not proof the file is gone. The design must
probe `exists`/length to determine actual state, retain the charge while the
file remains, record a `DeleteFailed`/`Orphaned` tombstone, expose a typed
degraded state, and provide a bounded explicit cleanup path. It must not spin on
a permanent failure, and it must never treat the bytes as free.

## Restart reconciliation (D4) — and the STOP

On cache initialization/reopen, a compliant design must enumerate cache-owned
files, validate their names/ownership, measure their lengths, and charge them
before admitting new materializations. A filename resembling a digest is **not**
proof of verified content: content-addressed orphans may only be reused after a
full length + SHA-256 verification; otherwise their charge is retained until
they are safely removed.

**This is blocked.** The approved `Directory` contract (S05) exposes only
`create`, `open_read`, `exists`, `delete`, `atomic_write` and `sync`. It has **no
enumeration and no length-before-open**, and S05 explicitly states there is no
public `list` operation. Without enumeration there is no way to discover
orphaned/temporary files left by a previous process, so the sum in the budget
equation cannot be computed honestly and a hard physical bound cannot be
claimed. Per Amendment #4 §7, execution stops here:

> Physical restart reconciliation requires a new/changed public `Directory`
> capability or alters approved S01–S16 semantics.

### Alternatives (for human decision)

1. **Extend `Directory` with a narrow enumeration/metadata capability
   (recommended).** Add reviewed methods such as
   `scan(&self, prefix: &StorageKey, visit: &mut dyn FnMut(&StorageKey, u64) -> Result<(), StorageError>)`
   and `file_len(&self, key) -> Result<u64, StorageError>`, implemented for
   `MemoryDirectory` and `FsDirectory` (root-confined `read_dir` +
   `symlink_metadata`, rejecting symlink components). The cache scans the cache
   namespace on `new`/reopen and charges each file. *Tradeoff:* changes an
   approved contract (S05/S11); needs conformance tests for both backends and
   restart tests. *Benefit:* one honest contract, directly supports D1/D4.
2. **Backend-specific crate-private `DirectoryIntrospection` extension trait.**
   Keep the public `Directory` trait frozen; add a `pub(crate)` trait with
   `scan`/`file_len`, implemented for the two backends, and require
   `D: DirectoryIntrospection` for the physical-bound cache. *Tradeoff:* still a
   new contract (hidden), and external `Directory` implementors cannot use the
   cache without implementing it; `SegmentCache<S, D>`'s bound tightens.
3. **Durable cache ledger instead of enumeration.** Persist a ledger of
   cache keys/lengths in the cache namespace; on restart, read it and `exists`/
   `open_read().len()` each key; name temp files deterministically so they can
   be probed. *Tradeoff:* introduces persistent metadata and a manifest-like
   format and crash-consistency protocol (against the "no manifest format"
   boundary), and still cannot discover genuinely orphaned files not in the
   ledger if the ledger write is lost.

**Recommendation:** option 1. It is the smallest honest change that makes the
budget equation computable, keeps a single contract, and is testable on the real
filesystem. Approval is required before any Phase C implementation.

## What is implemented today

Only the offloaded verification half of Amendment #4 (Phase A) is implemented:
SHA-256 for the full payload is computed on the filesystem worker inside the
same job that performs the atomic write, so it never runs on the async polling
thread and never copies the payload twice. The physical-byte ledger, failed-
delete retention, restart reconciliation and the A4-07..16 accounting tests are
**not** implemented.
