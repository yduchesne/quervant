# QOS-008 — Capability and State-Transition Reasoning

**Version:** 0.1-research-candidate  
**Status:** Prospective; **not approved**  
**Delivery:** Unscheduled, post-v0.1 research only  
**Authority:** Non-normative. This document does not amend approved QOS-001–QOS-004 or authorize implementation.

## Motivation and reference workload

Security posture analysis often asks whether an actor can reach a new capability through a sequence of individually authorized actions. For example, an AWS IAM principal might be permitted to pass a role to a service and control an execution context that uses that role. Whether this is a real privilege-escalation path depends on effective authorization, service-specific conditions, and actual control over the resulting context; graph connectivity alone is insufficient.

AWS IAM is a **reference workload**, not a built-in Quervant domain ontology. Other candidate domains include Kubernetes RBAC, Active Directory, Azure/GCP permissions, delegated application authorization and supply-chain capability paths.

## Fundamental distinction

Existing QOS-002 positive, monotonic least-fixed-point rules derive facts over a **fixed authoritative snapshot**. State-transition analysis explores **hypothetical states**:

`S0 --a1--> S1 --a2--> ... --an--> Sn`

Each action's preconditions and authorization must be evaluated against the state in which it occurs. Hypothetical mutations must never modify Quervant's authoritative indexed snapshot.

This is **not** equivalent to ordinary transitive graph reachability or to inferring `CanPerform` from an IAM Allow statement.

## Research questions requiring explicit approval

1. **Ownership boundary:** Should Quervant own a generic transition solver, or should an independent analysis engine consume Quervant's snapshot/ontology query APIs? **Working preference:** separate reasoning layer until a compelling generic core contract is demonstrated.
2. **Transition semantics:** How are typed capabilities, preconditions, effects, goals, hypothetical state identity, and state equivalence represented without arbitrary executable code?
3. **Authorization oracle:** How does the solver consult domain-specific effective-authorization evaluators, and how are evaluator versions, request contexts and incomplete inputs pinned?
4. **State search:** Which bounded algorithms, canonical state deduplication, pruning rules and cycle controls preserve soundness? What does exhaustive absence mean within a declared scope?
5. **Explanation:** How are supporting assertions, action preconditions, effects, policy decisions and unresolved assumptions exposed, potentially through QOS-005?
6. **Uncertainty:** How do results distinguish `CONFIRMED_PATH`, `CONDITIONAL_PATH`, `INDETERMINATE` and `NO_PATH_WITHIN_COMPLETE_SCOPE`? These names are illustrative, not approved API tokens.
7. **Time and changes:** How do pinned snapshot semantics interact with future QOS-007 temporal validity and changing authorization configuration?
8. **Isolation/security:** How are secrets, sensitive policies, cross-tenant data, and potential action-execution capabilities isolated? Analysis must be read-only by default.
9. **Performance:** What limits apply to search depth, states, branching, authorization checks, remote reads, memory, deadlines and explanation size?
10. **Scope of generality:** Which real workloads justify a reusable engine rather than domain-specific escalation-pattern detection?

## Candidate architectural separation (not decided)

1. **Quervant fact/query layer:** Snapshot-pinned asserted and inferred relationships, typed/lexical/temporal retrieval, canonical operator identities.
2. **Domain authorization adapter:** Effective-access decisions for a fully specified request and policy context; unsupported semantics produce unknown, not allow.
3. **Private hypothetical-state solver:** Evaluates preconditions, applies declared effects to an isolated state, explores bounded action sequences.
4. **Explanation layer:** Returns a reproducible path with evidence references, rule/evaluator versions, assumptions and completeness status.

A future design must specify how private hypothetical states are represented and queried without contaminating committed index generations.

## Required correctness principles for any eventual design

- **No false authorization from policy syntax:** A matching Allow is not equivalent to effective permission. Applicable denies, boundaries, organizational restrictions, session constraints, resource/trust policies, request conditions and service semantics must be accounted for by the domain evaluator.
- **Per-state validity:** Every step must be authorized and have satisfied preconditions in its immediately preceding hypothetical state.
- **No invented escalation:** A path to role association or resource creation is not proof of exercising the role's privileges.
- **Explicit incompleteness:** Budget exhaustion, unsupported actions, missing policy inputs and unresolved conditions cannot be reported as a conclusive no-path or confirmed path.
- **Deterministic replay:** Pin the initial snapshot, ontology/operator semantics, authorization evaluator version, domain model, goal and search parameters.
- **Non-interference:** Hypothetical actions cannot mutate authoritative Quervant data or execute cloud API operations.
- **Bounded exploration:** Hard resource budgets and cancellation, with explicit outcomes.
- **Explainability:** Every claimed path identifies its steps, supporting facts and unresolved assumptions; derived logical facts are not probabilistic attribution.
- **General-purpose core:** No AWS IAM-specific concepts hardcoded into the ontology or storage engine.

## Future acceptance gate (research, not implementation)

Before approving QOS-008, produce:
- A decision record comparing embedded solver versus separate analysis engine, including operational and semantic tradeoffs.
- A formal small-step transition model and a scoped effective-authorization adapter contract.
- At least two distinct reference domains demonstrating reusable abstractions.
- Counterexamples for policy Allow-versus-effective-access, stale authorization, false reachability, cyclic transitions, and incomplete search.
- A bounded-result contract with soundness/completeness claims and independently checkable path witnesses.
- A compatibility analysis with QOS-002 monotonic inference, QOS-003 snapshot semantics, QOS-003C invalidation, QOS-004 operator resolution, and proposed QOS-005 explanations.
- Explicit user approval before changing the architecture baseline or creating implementation plans.

## Out of scope

No built-in AWS ontology, IAM evaluator, cloud API executor, attack simulation, automatic privilege escalation, probabilistic attribution, or implementation PR is approved by this proposal. Quervant v0.1 scope remains unchanged.
