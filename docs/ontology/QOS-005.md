# QOS-005 — Inference explanation and provenance interfaces

**Version:** 0.1-proposal | **Status:** proposed, **not approved** | **Delivery:** post-v0.1, unassigned

## Motivation

Ontology inference can return a derived fact without showing which asserted facts and rules justify it. Evidence-oriented consumers, including ATI (Agentic Threat Investigator), need reproducible, bounded explanations linked back to their own evidence and observations. QOS-005 is an **architectural candidate**, not a retroactive amendment to approved QOS-001–QOS-004 semantics and not an implementation authorization.

## Proposed goals

1. Explain why an effective relationship or class-membership predicate is true in a **specific pinned snapshot**.
2. Distinguish **asserted** facts from **inferred** conclusions, including applied rule/archetype identity and version.
3. Return bounded derivation witnesses referencing canonical asserted relationship keys, instance incarnation IDs and optional caller-supplied opaque provenance references; never invent source evidence.
4. Support multiple independent proofs without requiring enumeration of every proof or persistent materialization of all inference results.
5. Make explanation results deterministic under a specified canonical ordering, subject to explicit resource budgets.
6. Permit consumers to resolve provenance references in their authoritative systems; Quervant does not become an evidence or provenance system of record.
7. Preserve PIT isolation, ontology semantic fingerprints, and retraction correctness from QOS-003A/B/C.

## Proposed logical interface (non-normative)

An explanation request identifies:
- Pinned index/snapshot identity and ontology semantic fingerprint.
- Canonical operator or relationship identity and fully bound arguments.
- Optional explanation mode: one witness, up to N independent witnesses, or a bounded proof graph.
- Explicit limits for recursion depth, rule applications, nodes/edges, output bytes, elapsed time and remote I/O.

A successful response identifies:
- Requested conclusion and whether it is **asserted** or **inferred**.
- A stable, snapshot-local explanation ID (not a globally durable fact ID).
- Rule/archetype identifiers and version/fingerprint for derivation steps.
- Supporting asserted triples and optional opaque provenance references.
- Whether the response is **complete** with respect to the requested proof enumeration or a **bounded partial explanation**.

A bounded partial explanation is **not** evidence that additional proofs do not exist. Failure to find a proof within budget must never be reported as a conclusive false result. Distinguish `PROVEN`, `DISPROVEN_COMPLETE`, and `INDETERMINATE` at the query-result level; explainability may also report `PROVEN_WITH_PARTIAL_EXPLANATION` when a conclusive witness exists but enumeration is incomplete. Exact API types and naming remain undecided.

## Proposed correctness requirements

- **Soundness:** Every returned proof step is valid under the snapshot-pinned compiled ontology, and every leaf corresponds to a visible asserted fact or a valid built-in axiom.
- **No cyclic self-support:** Recursive derivations must be grounded; a cyclic chain of inferred facts alone is not a proof.
- **Retraction awareness:** A witness that depended on a retracted assertion is not valid in a later snapshot; alternative proofs may remain.
- **Identity safety:** Explanations use immutable instance incarnation IDs, never remap deleted instances through reused external keys.
- **Reproducibility:** Same snapshot, query, ontology and budget/ordering settings produce semantically equivalent explanation results independent of compaction.
- **Integrity:** Missing/corrupt authoritative relationship data fails closed; a corrupt disposable proof cache may be rebuilt.
- **Non-interference:** Explanation generation does not mutate asserted facts or alter inference/query truth values.
- **Separation of concerns:** Opaque evidence references are supplied and resolved by the caller, not inferred or fabricated by Quervant.

## Design options requiring future approval

| Topic | Alternatives / question |
| --- | --- |
| Proof representation | Derivation tree vs DAG with shared subproofs; canonicalization |
| Proof generation | On-demand backward tracing vs optional materialized supports |
| Multiple proofs | One canonical witness vs bounded enumeration; proof independence definition |
| Recursive explanations | Finite grounded witness extraction and SCC handling |
| Provenance binding | Assertion-level opaque reference vs future occurrence/provenance model |
| Temporal claims | Observation time and validity intervals are **not** inferred from snapshot time |
| Security | Per-reference access controls, redaction and cross-boundary leakage |
| API | Typed query IR extension, response schema, streaming and pagination |
| Resource semantics | Proof count, depth, fan-out, memory, deadline and truncation signaling |
| Persistence | Snapshot-local cache vs durable proof artifact; garbage collection |

## ATI reference scenario (illustrative)

ATI indexes observed `resolves_to(domain,ip)` and `announced_by(ip,asn)` facts with opaque references to its PostgreSQL evidence observations. A declarative ontology may derive a domain-to-ASN infrastructure association. An explanation response could identify the two asserted edges, the rule used, and their evidence references; ATI would resolve those references and display observation timestamps, source provenance and analyst context.

**Safety boundary:** Such an association does not imply maliciousness, attribution, causation, or temporal overlap. Quervant must not silently upgrade logical derivation into evidentiary confidence.

## Acceptance criteria for a future approved design

- Explicit proof semantics and typed result contract.
- Independent reference-evaluator proof validation for small ontologies.
- Differential tests across multiple proofs, recursive grounding, retractions, PIT, compaction and recovery.
- Conclusive-vs-partial behavior under budgets; no false negatives from exhaustion.
- Provenance references survive segment merging without implying source-of-truth ownership.
- No ontology implementation PR until Quervant v0.1 is complete.
